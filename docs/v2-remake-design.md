# バトルフロンティアⅡ（リメイク版）設計メモ

インフレしすぎた旧版を作り直すためのv2。**旧版のコードとデータには一切触れない**方針で、
同じリポジトリ・同じSupabaseプロジェクトの中に完全に分離して置く。

## 置き場所と切替

| 種別 | 旧版 | v2 |
|---|---|---|
| コード | `src/pages` `src/lib` | `src/v2/pages` `src/v2/lib` |
| ルート | `/game` ほか | `/v2` |
| テーブル | `profiles` ほか | `v2_` 接頭辞（`v2_profiles`） |
| SQL | 既存の各ファイル | `supabase_v2_core.sql` |

- 切替は街（`/game`）の☰メニュー →「🧪 リメイク版に切替[開発]」。PC/モバイル両方のメニューに設置。
- v2は **is_admin 限定**。非管理者が `/v2` を直接開いた場合は `reportDevAccess` で通知して `/game` へ戻す。
- キャラクターは旧版と別物。同じアカウントで両方遊べる。

## ステータス（あるけみすと準拠）

8種。正は [`src/v2/lib/stats.js`](../src/v2/lib/stats.js)。

| キー | 表示 | 意味 | 効果 | unit |
|---|---|---|---|---|
| `hp` | HP | 生命 | 0で戦闘不能 | 8 |
| `mp` | MP | 魔力 | スキル使用で消費 | 3 |
| `str` | STR | 腕力 | 通常攻撃と物理スキルの威力 | 1 |
| `dex` | DEX | 器用 | 命中率・ダメージの安定度（振れ幅の下限） | 1 |
| `agi` | AGI | 敏捷 | 行動順・行動回数・回避 | 1 |
| `int_stat` | INT | 知性 | 魔法攻撃の威力と魔法防御 | 1 |
| `vit` | VIT | 耐久 | 被ダメージ（回避・魔法防御にも軽微） | 1 |
| `luk` | LUK | 幸運 | クリティカル率・回避率 | 1 |

- `unit` = 抽選1回で上がる量。同時に「戦闘力1あたりの必要量」でもある（HP8＝戦闘力1）。
- 列名が `int_stat` なのは `int` がSQLの型名のため。JS側のキーも同じ `int_stat` に揃えてある（対応表を作らない＝ズレようがない）。
- **防御は独立ステータスを持たない**。あるけみすと同様、物理防御は VIT、魔法防御は INT と VIT から算出する
  （あるけみすとの式は 物理 `VIT×1.0〜0.5` / 魔法 `INT×1.0〜0.5 + VIT×0.15`）。実装は「ダメージと判定」を参照。
- **AGIの行動順・行動回数**も実装済み（「ダメージと判定」の項を参照）。

## 成長

- LVアップ1回につき **5回抽選**し、当たったステータスが `unit` だけ上がる。
- 8種すべて **均等 1/8**。当たりやすさを偏らせる「手相」は未採用（後から足せる）。
- どのステに当たっても戦闘力の上がり幅は同じ（1回＝戦闘力+1、1LV＝+5）。
- LV上限 **100**。上限到達後はEXPが入らない（転職待ち）。
- 必要EXPは **60** スタートで、**転職100回ごとに +10、100で打ち止め**
  （`min(100, 60 + floor(転職回数 / 100) × 10)`）。転職100回で70、200回で80、300回で90、400回以降は100。
  あるけみすとも転生数に応じて 70→80→90→100 と重くなる。`EXP_STEP_PER_JOBS` で変えられる。
- 初期ステータスは暫定値（HP40 / MP12 / 他5）＝戦闘力39スタート、LV100で534。
  あるけみすとの公表値が見つからなかったため決め打ち。`INITIAL_STATS` だけ直せば変えられる。

## 転職（あるけみすとの「転生」に相当）

- LV100でのみ実行できる。**LV1に戻り、ステータスは初期値へリセット**される。
- そこへ **「転職回数×100」戦闘力分**（100＝20LV分）を8種へランダムに振り分ける。
  前回の配分は引き継がず**毎回引き直し**（あるけみすとの「初期ステータスに転生回数×125を振り分ける」と同じ形）。
- 到達点は周回ごとに100ずつ上がる。

| 転職回数 | 転職直後の戦闘力 | LV100時 |
|---|---|---|
| 0 | 39 | 534 |
| 1 | 139 | 634 |
| 2 | 239 | 734 |
| 5 | 539 | 1034 |

- 転職では**転職先の職業を選ぶ**。選んだ職業の回数（`job_counts`）が1増え、上位職の条件はこれを見る。

## 職業

マスタの正は **DBの `v2_classes`**（`supabase_v2_core.sql` でシード）。クライアントはこの表を読んで表示するだけで、
JS側にマスタは持たない（二重定義を作らないため）。条件の判定はサーバー（`v2_change_job`）が行う。

- 開始時は **ノーブル**（転職先には選べない）
- 条件は2種類だけ。**「その初期職での転職回数」** と **「〈職業名〉の証」**
- 証の名前は全職業とも `職業名 + の証` で統一（`proofOf()` で導出できる）
- **証は転職のときに1個消費する**。そのため所持は個数で持つ（`proofs` = `{"侍の証":2}`）。
  同じ上位職にもう一度転職するには証をもう1個入手する必要がある
- 同じ職業に何度でも転職できる（上位職の条件を満たすには同じ初期職で3回必要）

| 区分 | 職業 | 条件 |
|---|---|---|
| 初期職 | 戦士 / 弓使い / 魔法使い / 僧侶 / 格闘家 / サモナー | なし |
| 上位職 | 侍・狂戦士 | 戦士で転職3回＋証 |
| | 狩人・暗殺者 | 弓使いで転職3回＋証 |
| | 元素使い・死霊使い | 魔法使いで転職3回＋証 |
| | 聖職者・異端審問官 | 僧侶で転職3回＋証 |
| | サイキッカー・体術師 | 格闘家で転職3回＋証 |
| | 精霊召喚士・式神使い | サモナーで転職3回＋証 |
| 複合上位職 | 魔法剣士 | 戦士3回＋魔法使い3回＋証 |
| | 魔銃士 | 弓使い3回＋魔法使い3回＋証 |
| | 聖騎士 | 僧侶3回＋戦士3回＋証 |
| | 賢者 | 魔法使い3回＋僧侶3回＋証 |
| | 武僧 | 格闘家3回＋僧侶3回＋証 |
| | ビーストレンジャー | サモナー3回＋弓使い3回＋証 |
| 特殊職 | ギャンブラー / 竜騎士 / ブリーダー | 証のみ |

- 成長は職業に関係なく均等ランダム。職業の差は**スキル**と**職業補正**の2つで付ける。
- **証の入手手段もまだ無い**。確認用に `v2_debug_grant_proofs`（is_admin限定）で全種類を1個ずつ足せるようにしてある（押すたびに在庫が増える）。

### 職業補正（常時発動・枠を使わない）

正は [`src/v2/lib/classBonus.js`](../src/v2/lib/classBonus.js)、一覧は [v2-skills.md](v2-skills.md)。

- **その職業に就いている間だけ**ずっとかかる。スキルセットの5枠は使わない
- 転職して別の職業になった時点で効かなくなる
- **上位職・複合上位職・特殊職だけが持つ**。初期職6職とノーブルは補正なし
  （初期職は通過点なので数字を増やさない／上位職に就いた実感を出すため）
- 幅は ±5% が基本。狂戦士だけ STR+10%・VIT-5%、異端審問官は INT+10%・自身の回復量0.8倍、
  ギャンブラーは LUK+10%（＝クリティカル率）と、尖らせたぶんを別の形で払わせている

★**これが「いまの職業」に意味を持たせている唯一の要素**。スキルは習得済みで転職後も残るので、
職業補正が無いと現在の職業はただのスキル習得先になってしまう。

#### 転職を重ねると伸びる（2026-08-16 追加）

**その職業に何回転職したか**（`v2_profiles.job_counts`）で職業補正が伸びる。
同じ職業を選び続ける動機を作るための仕組み。

| | 伸び方 |
|---|---|
| 伸び始め | **2回目の転職から**（1回目はもともとの補正値のまま） |
| メインステータス | 1回ごとに **+0.1%** |
| サブステータス | **5回ごとに +0.1%** |
| 100回を超えたぶん | 上がり幅が**半分**（メイン+0.05%／サブは5回ごと+0.05%） |

例：侍（STR+5%・main STR／sub DEX）に11回転職 → **STR+6%・DEX+0.2%**。
201回なら STR+20%・DEX+3%（100回ぶん満額＋100回ぶん半額）。

★**どのステがメインでどれがサブかはマスクデータ**。画面に出すのは「いまの職業補正がいくつか」だけで、
割り振りも伸び方も公表しない。⚠これを画面に出す実装を足さないこと（出すなら別途指示をもらう）。
割り振りの正は `CLASS_BONUS` の `main` / `sub`。

★サーバー側の変更は不要。`job_counts` は `v2_change_job` がすでに職業ごとに数えていて、
戦闘はクライアントの `runBattle` が回すため、`classBonusOf(cls, count)` を通せば全戦闘に効く。

## ダメージと判定

正は [`src/v2/lib/combat.js`](../src/v2/lib/combat.js)。あるけみすと準拠。

- 物理は **STR**、魔法は **INT** に**スキルの倍率**を掛ける
- 防御は**引き算ではなく％軽減**、しかも**上限がある**（物理は最大34%・魔法は最大50%）
  - 防御力＝物理は `VIT`、魔法は `INT + VIT×0.15`（防御専用ステータスは持たない）
  - あるけみすとの表記は `VIT×1.0〜0.5` / `INT×1.0〜0.5 + VIT×0.15`。主ステの係数は物理も魔法も
    同じ「1.0〜0.5」なので、**起点の1.0で揃える**（逓減は下の軽減率の式が担う）
  - ⚠ 2026-08-12まで物理だけ1.0・魔法だけ0.5と取り違えていて、**魔法防御が半分**になっていた
  - **魔法は軽減上限が高い（50%）うえに防御力も厚い**（同じステなら `INT+VIT×0.15` > `VIT`）ので、
    同じ倍率でも物理より通らない。**だから魔法スキルの倍率は物理より高く置く**
    （あるけみすとも同じ：魔法はINT×2.6・3.55、物理はSTR×2.2〜2.4）
  - 軽減率＝`上限 × 防御 / (防御 + 攻撃)`。防御をいくら積んでも上限に漸近するだけでダメージは0にならない
  - 旧版の「硬すぎて削れない／柔らかすぎて溶ける」の二極化を構造的に防ぐのが狙い
- クリティカルは**倍率×1.5＋1.5**かつ**相手の防御力÷1.5**（≒防御の1/3を無視）
  - **判定の順番もあるけみすと準拠**：先にクリティカルを決め、そのあと命中判定する。
    クリティカルの命中判定では **DEX×1.5 ＋ LUK÷3** をDEXとして扱う＝クリは通常より当たりやすい
  - **クリティカルするスキルとしないスキルがある**（あるけみすとも同じ。ゲーム内には表記されない）。
    スキル側の `noCrit` で指定する。逆に確定クリティカルは `sureCrit`（あるけみすとの破魔の一撃・刺閃に相当）
  - ⚠ `＋1.5` は**元の倍率によらない固定加算**なので、**倍率が低いほど伸び率が大きい**
    （0.57倍→約4.0倍／1.9倍→約2.4倍）。あるけみすとも「手数のあるスキルでクリティカルすると
    総係数への恩恵が大きい」と明記していて、低係数の刺閃や破魔の一撃が強いのはこれが理由。
    **v2では多段スキルを `noCrit` にして、そのぶん素の倍率を上げる**（そうしないと多段が壊れる）
- スキルは**発動率**を持ち、毎ターン抽選する（強い技ほど出にくくする）
- 命中は **「100% − 回避率」**。回避率はステータスから出す
  - 回避スコア＝`AGI + VIT×0.1 + LUK×0.1` ／ 回避率＝`104 × (回避スコア/(回避スコア+DEX))⁵`
    （`104` は上限ではなく係数。実際の上限は `EVA_RATE_MAX = 75%` ＝命中は最低25%）
  - あるけみすとも「回避率+3%」「10%の確率で外れる」と**回避率を独立した%で持っている**ので、
    そこに合わせた形（式そのものは非公表なのでBF独自）
  - パッシブの「最終命中率+5%」「回避率+5%」は、この回避率へ素直に足し引きする
- **狙い（2026-08-14 再較正）：同格ではほぼ当たるが、差がつくと一気に当たらなくなる**
  - 装備でステータスを狙って伸ばせるので、AGI型・DEX型を作った意味が出るようにする

| 相手のAGI（自分基準の倍率） | 1倍 | 1.5倍 | 2倍 | 3倍 | 5倍 | 10倍 |
|---|---|---|---|---|---|---|
| 命中率 | 95% | 89.8% | 84.1% | 73.4% | 57.0% | 35.1% |
| 自分のDEXを3倍に積んだ場合 | 99.8% | 99.4% | 98.6% | 96.2% | 89.4% | 71.5% |

  - DEXで取り返せる幅は最大**+36ポイント**（旧式は最大+14しかなかった）
  - ⚠曲線を6乗まで立てると、AGI20倍あたりで回避が上限に張り付き、
    **DEXを積んでも取り返せない区間**ができる。5乗で止めているのはそのため
  - ⚠2026-08-13までは `35% ×(比)²` で、相手AGIが10倍でも命中71%と差が潰れていた

### スキルごとの命中率（acc）— 枠だけ先に用意

```
最終命中率 = acc +(100 − acc)× 安定度 − 相手の回避率
安定度   = DEX /(DEX + 自分の主ステータス)   ※ダメージの下限と同じ指標
```

- **いまは全スキル acc=100**。そのとき式は `100 − 回避率` になり、命中率を持たない技と完全に同じ挙動
- 当てにくい大技を出したくなったら、その技だけ acc を下げる
- ★**引き算（acc − 回避率）にしない**のが要点。引き算だと天井が下へ移動するだけで
  DEXの伸びしろが増えない（下の表）。「足りないぶんをDEXが100%へ向けて埋める」形にすると、
  **命中率の低い技ほどDEXが効く**＝DEX型が「当てにくい大技を実用にする型」になる

| スキル命中率 | 同格 | DEX2倍 | DEX5倍 | DEXの伸びしろ |
|---|---|---|---|---|
| 100%（既定） | 95% | 99.2% | 100% | +5.3% |
| 90% | 90% | 95.9% | 98.3% | +9.3% |
| 80% | 85% | 92.5% | 96.7% | +13.7% |
| 70% | 80% | 89.2% | 95% | +18.8% |
| 60% | 75% | 85.9% | 93.3% | +24.4% |

⚠**発動率とは別の確率なので掛け算になる**。発動75%×命中80%だと実際に当たるのは63.8%。
accを下げるのは一部の技だけにすること。多段は1発ずつ判定するのでさらに荒れる。

### ダメージの振れ幅（DEXの2つ目の仕事）

```
ダメージ = 素の値 ×(下限 〜 1.00 の乱数)× 1.194
下限     = 1 − 0.65 ×(1 − DEX /(DEX + 自分の主ステータス))
```

- 同格は **0.68〜1.00倍**、DEXを3倍積むと **0.86〜1.00倍**（振れ幅が縮む）
- 末尾の `1.194` は幅を入れたぶん平均が下がるのを戻す係数（`1/(1 − 0.65/4)`）。
  **平均ダメージは幅を入れる前と同じ**

**なぜ要るか。** 命中には100%という天井があるので、DEXは命中だけだと
**伸ばしても+11%の保険**にしかならず、しかも相手が鈍いと文字通り無価値だった。
実測では戦闘力+150をDEXに全振りしても同格への勝率62.9%（同じ戦闘力をSTRに振れば75.4%）で、
HP・MPを除けば最下位。この下限管理を足して **73.7%** となり、STR（74.4%）・INT（74.7%）と並んだ。

⚠**安定度は「DEX vs 自分の主ステータス」で測る。相手とは比べない。**
相手基準にすると、AGI型が相手のときに下限が上がらず**一番必要な場面で効かない**
（実測でDEX型のAGI型への勝率が27.9%止まりだった。自分基準なら32.3%）。
自分基準でもスケール不変は保てる。

考え方の出どころはラグナロクオンラインの「DEXが最小攻撃力を底上げする」。
あるけみすとの表記 `STR×倍率×(1.0〜0.66)` も幅を持っているので、そちらにも寄る。

### ステータスを伸ばす価値（実測）

⚠**勝率で測ると100%で頭打ちになって差が潰れる**ので、
**「同格に勝率75%で勝つのに、そのステへ戦闘力をいくら積む必要があるか」**という交換レートで測る。
小さいほど強いステ。
⚠**STRは物理職・INTは魔法職でしか働かない**ので、測るときは職業を分けること
（混ぜて平均すると両方とも実際より弱く出る。2026-08-14にこれで誤った数字を出した）。

| | INT | HP | STR | AGI | LUK | DEX | VIT | MP |
|---|---|---|---|---|---|---|---|---|
| 必要な戦闘力 | 10 | 12 | 12 | 40 | 80 | 200 | 278 | 届かない |

⚠**バランスは取れていない。装備で伸びる5種だけでも 10〜278 と28倍の開きがある。**

原因は構造的で、**攻撃ステは線形で上限が無いのに、守り系は全部「上限つきの%」**だから。

| ステ | 伸ばしきったときの上限 |
|---|---|
| STR・INT | **上限なし**（倍率にそのまま乗る） |
| AGI | 回避 最大75%（被ダメ1/4）＋行動順＋追加行動50% ＝ 実質6倍相当 |
| VIT | 軽減の上限が 物理34%・魔法50% ＝ 被ダメ最小66%/50%（最大2倍） |
| DEX | 命中×1.05 × 安定度×1.19 ＝ **×1.25** |

→ **装備の数値を大きくしても埋まらない**（DEXに戦闘力+1000積んでも勝率81%・VITは89%で天井）。

**この開きは仕様として受け入れる（2026-08-14 決定）。** v2の土台はあるけみすと式
（VITは被ダメージだけ・DEXは命中だけ）で、**AGIとDEXの2つにだけ他ゲームを参考にした仕事を足す**、
という切り分けにする。検討した「VITが最大HPにも乗る」「DEXが攻撃力にも乗る（ラグナロク式）」は
交換レートを 9〜38（4.2倍）まで詰められたが、**あるけみすとの構造から離れるので不採用**。

そのぶん**装備の数値でバランスを取る**。⚠ただしVITとDEXには天井があるので、
いくらでも数値を盛れるわけではない。有効レンジは**どちらも「主ステの3倍」あたりまで**：

| 主ステに対する倍率 | 1倍 | 2倍 | 3倍 | 5倍 | 10倍 | 30倍 |
|---|---|---|---|---|---|---|
| DEX：通るダメージ | ×1.000 | ×1.112 | ×1.152 | ×1.189 | ×1.220 | ×1.244 |
| VIT：物理の被ダメージ | 83.0% | 77.3% | 74.5% | 71.7% | 69.1% | 67.1% |

2倍までで伸びの大半を取り、3倍を超えると1段ごとに数%しか動かない。
**装備でDEX/VITを主ステの3倍より上へ持っていける設計にすると、その先は捨て値になる。**

⚠**防具にVIT/DEXだけを載せると誰も着けない**（同じ数値ならSTR/INTのほうが16〜28倍効率がいい）。
防具にもSTR/INTを載せるか、数値以外の特殊能力で価値を作ること。

- **HPとMPは装備で増やさない**（装備で伸びるのは STR / DEX / AGI / VIT / INT の5種だけ・2026-08-14 決定）
- MPは天空闘技場（HP/MPが回復しない連戦コンテンツ・実装予定）と、消費MPが増えるほど威力が上がるスキル（同じく予定）で意味を持たせる
- ⚠**AGIの強さは追加行動から来ていない**。追加行動を0%にしてもAGIは強いまま。本体は回避と行動順
- ⚠**INTがSTRより1.8倍安い**。INTは魔法攻撃・魔法防御・回復量の3役を持つため（あるけみすとも同じ構造）
- 型どうし：DEX型はAGI型に32.3%（旧21.2%）・均等に74.1%（旧62.3%）

### 行動順と行動回数（AGI）

あるけみすとは「AGIは行動順・行動回数・回避に影響」としか公表していないので、**ここは旧版（無印）準拠**。
ただし**上限を付け直している**。

- **行動順**：スキルの `priority` → AGI → 同値ならランダム。**順番が変わるだけで行動回数は増えない**
  - `0` … 攻撃スキルと通常攻撃
  - `1` … **補助・回復（既定）**。攻撃より先に動けるが、2以上には後攻になる
  - `2以上` … さらに先に動く枠。上位職の切り札などに使う（いまは未使用）
- **行動回数**：**相手よりAGIが高いときだけ**、確率で追加行動。
  AGI比 1倍で0%、**10倍で50%に到達してそこで打ち止め**（`extraActionRate`）

⚠ ここが旧版との一番大きな差。旧版は `(自SPD−敵SPD)/敵SPD×50` で**上限が無く**、
2倍差で50%・3倍差で75%…と伸び続けた。転生（転職）で差がつくほど一方的になる＝インフレの温床だった。

| 534（0転職） | 67 | 1.00倍 | 0% | 0% |
| 634（1転職） | 79 | 1.19倍 | 1.0% | 9.4% |
| 1034（5転職） | 129 | 1.94倍 | 5.2% | 46.8% |
| 2034（15転職） | 254 | 3.81倍 | 15.6% | 95.2% |
| 5334（48転職） | 669 | 9.99倍 | **50%（上限）** | 249.7% |

**この式はスケール不変**：同格どうしなら戦闘力がいくつでも殴り合いのテンポが変わらない。

## 戦闘ループ

正は [`src/v2/lib/battle.js`](../src/v2/lib/battle.js)。純関数（`rng` を渡せば結果が再現する）。

スキルの回り方は**あるけみすと準拠**で、旧版のスキルセット（順番＋使用回数）とほぼ同じ形：

- セットした枠を順に1巡し、それぞれの枠の**使用回数**だけ使う（ABCDE→ABCDE…）
- 使用回数を使い切った枠・空の枠・**MPが足りない枠は飛ばす**（使用回数は減らない）
- **不発のときは MP も使用回数も減らず、ポインタも進まない**（同じ枠を撃ち直す）
  → 発動率の低い技を上に置くとそこで詰まる。**並び順と使用回数の配分がプレイヤーの選択**
- 不発のターンと、撃てる枠が無いときは**通常攻撃**（倍率1.0・消費MP0。物理職はSTR・魔法職はINT参照）
- 1ターン＝行動順（優先度→AGI）で両者が1回ずつ行動し、AGIが上なら確率で追加行動
- ターン終了時に持続回復（祈祷・魔力供給）とバフの残ターンを処理する
- 100ターンで引き分け。HP/MPは戦闘開始時に満タン（旧版の「宿屋廃止」方針を引き継ぐ）
- **ステータスの増減バフは戦闘中ずっと続き、重ねがけで加算される**（あるけみすと準拠。
  向こうも「重ね掛け可能」「回避成功毎に+3%」と累積前提で、バフ側にターン数の記載が無い。
  ターン数が明記されているのは麻痺1T・沈黙2Tなどのデバフ側）。下限は-90%
- **状態異常は5種（出血・毒・鈍足・麻痺・回復阻害）が入っている**（`ailments.js`）。
  出どころは**エンチャントの特殊能力**と、**スキル自身が持つ `ail`**（敵の技だけ・2026-08-17）。
  付与は「当たったとき」だけで、相手のエンチャント抵抗（`ailResist`）を引いてから判定する
  （`battle.js` の `tryInflict`）。⚠**プレイヤーのスキルにはまだ `ail` を付けていない**

### バランスの測り方

**職業ごとの勝率で測ってはいけない。** 転職でランダムにスキルを覚えていくので、
最終的にどの職業でもいろんなスキルを使えるようになる＝職業単位の比較に意味がない。

正しい測り方は**スキル単体の価値**。基準スキル（体当たり STR×1.4／95%／MP5）だけのビルドと戦わせて、
勝率50%が「基準と同じ価値」。攻撃スキルはそれだけを撃ち続け、補助・回復は1〜2回使ってから基準攻撃に移る形で測る。
検証スクリプトは scratchpad の `skillvalue.mjs`。

調整後の実測（LV100・0転職を1200体・各800戦）：

| 勝率 | スキル |
|---|---|
| 64〜60% | 剛射・アイスランス・鉄拳・強撃・グリフォン召喚・精神統一・サンダー・ファイア・狙撃 |
| 57〜53% | ライトニング・プロテク・疾風矢・群れの号令・狙い撃ち・シールドアタック・祈祷・爆裂拳・小悪魔召喚・打撃・連打 |
| 52〜40% | 残心・体当たり・駆け足・貫通射撃・気合い・ライト・防御態勢・オオカミ召喚・マジックアロー・防御崩し・はたく・身構える |
| 34〜16% | ヒール・応急手当・魔力供給 |

**発動率は85%以上に置く。** あるけみすとも75〜100%が大半で、60%以下はメテオストライク60%・
フルハウス20%くらい（旅人＝初期職も 95/85/80%）。**強さの調整は発動率を削るのではなく倍率で行う。**
発動率を50%台まで下げると初期職としては出ない技だらけになる。

## スキルの習得中・習得済み・編成

**スキルは2段構え**（あるけみすと準拠だが名前はv2独自。[基本情報](https://wikiwiki.jp/alchemist-p/%E5%9F%BA%E6%9C%AC%E6%83%85%E5%A0%B1)の「スキル」の項）。

| | 増え方 | 転職したとき |
|---|---|---|
| **習得中** | **LVアップ時に、いまの職業のスキルを確率で覚える** | **失われる** |
| **習得済み** | 転職のとき、いまの職業の**習得中のスキル**から1つ | ずっと残る |

- **使えるスキル ＝ 習得中 ∪ 習得済み**。職業に就いただけでは使えない
- LVアップの習得率は **15%**。加えて「残りLV数が未習得数を下回るぶん」は確定で覚えるので、
  **LV50までに必ずその職業の5個が全部そろう**（`LEARN_BY_LV` / `LEARN_PCT` / `forcedLearnCount`）
- 習得済みにできるのは「いまの職業の**習得中でまだ習得済みでない**」スキルだけ。
  全部習得済み／そもそも習得中が無い場合は**何も残らない**
- **転職で使えなくなったスキルは編成から自動的に外れる**（サーバー側 `v2_change_job` が刈り込む。画面側にも保険あり）
- → **周回するほど習得済みが増え、どの職業でもいろんなスキルを使えるようになる**
- → **だから職業ごとの勝率でバランスを測っても意味がない**
- 編成は **5枠**。各枠に「どのスキルか」と「使用回数」を設定する。**並び順＝発動順**
- **使用回数の上限は「想定利用MP（Σ 消費MP×回数）が最大MPを超えないこと」**で決まる
  - あるけみすとの「あなたの最大MPは◯MPです／想定利用MPは◯MPです」と同じ考え方
  - **MPを伸ばすほど強い技を多く積める＝MPがステータスとして効く**
  - **1周ごとに次の枠へ回る**（体当たり2回・強撃1回なら 体当たり→強撃→体当たり）
  - 使い切ったら通常攻撃になる

一覧は**検索・種別タブ（物理/魔法/補助/回復/パッシブ/お気に入り）・並べ替え（名前/MP/発動/職業）・お気に入り**で絞り込める。
スキルが増えても探せるようにするため（あるけみすとの画面と同じ作り）。

### パッシブ（`kind:'passive'`）

上位職21職が1つずつ持つ。**スキルの枠に入れて使う**（職業補正とは別物）。

- **発動率も使用回数も持たない**（枠に入れておくだけで常時効く）
- **消費MPも持たない**＝想定利用MPに数えない
- **発動順のローテーションには入らない**。`createSide` が枠から分けて常時効果として扱う
- **複数セットできる**。そのぶん1つ1つは控えめにして、枠を通常スキルに使うメリットを残す
- 効果は `passive:{...}` に書く。書ける項目は `PASSIVE_EFFECT_KEYS`（`skills.js` の表を参照）で、
  解釈するのは `battle.js` の `collectPassives` / `liveStats`

★**単なる「ステータス+N%」は職業補正の担当**にして、パッシブ側は
ステータスでは書けない挙動に寄せてある：不発時の通常攻撃2倍（居合の構え）／
ダメージを与えるたびスタック（バーサク・執行本能）／最終命中率・クリ率・発動率・貫通への直接補正／
直前と違うスキルで強化（元素共鳴）／HPが減るほど強化（闘争本能）／
デバフを1回打ち消す（心身一如）／確率で威力が振れる（ギャンブルボディ）など。

一覧は [v2-skills.md](v2-skills.md)。
⚠精霊召喚士・式神使い・ビーストレンジャー・ブリーダーの4職は効果を保留中（暫定でステータス補正）。

DBは `v2_profiles` の `skills`（習得中・転職で失う）・`learned`（習得済み・ずっと残る）・`skill_set`（編成）・`favorites`（お気に入り）。
スキルの名簿は **`v2_skills` テーブル**（名前・職業・消費MP）にあり、サーバーの習得抽選と編成の検証はこれを見る。
**倍率などの数値は `skills.js` のまま**なので、⚠スキルを増やす／消費MPを変えるときは両方直すこと。

## スキル

正は [`src/v2/lib/skills.js`](../src/v2/lib/skills.js)。**名前は旧版から流用、倍率・発動率・消費MPはv2で新規**。
参照するステータスはv2の8種（物理=STR / 魔法=INT、副参照でAGI・VIT）。

- 倍率の置き方（**2026-08-18 改定**）：基準は**あるけみすとの物理レンジ STR×2.2〜2.4**。
  上位職の**合計倍率（主参照＋副参照）×多段数**の上限を **物理2.4／魔法2.7** に置く。

  | 区分 | 通常(90%) | 主力(85%) | 切り札(75〜82%) |
  |---|---|---|---|
  | 上位職・物理 | 1.7〜1.9 | 2.0〜2.2 | **2.4** |
  | 上位職・魔法 | 1.9〜2.15 | 2.25〜2.45 | **2.7** |
  | 初期職 | 物0.8〜1.65 ／ 魔1.3〜1.85（発動率85〜100%） | | |

  ⚠**改定前は上位職の切り札を3.0〜4.0（天墜竜閃4.0・メテオストライク0.95×4）まで伸ばしていて、
  あるけみすとの倍近くになっていた**。上位職の伸びしろは倍率ではなく職業補正とパッシブで出す。
  上限は「合計」で見ること。単体の `mult` だけ見るとエレメンタルエッジ 2.2＋INT×1.0＝3.2 のような
  技がすり抜ける（`skills.test.js` の「上位職の合計倍率があるけみすとの水準を超えない」で固定）
- **魔法の倍率は物理より高く置く**。魔法は軽減上限50%＋防御力も厚いので、同じ倍率では通らない。
  v2の式では**魔法は物理の1.13倍でちょうど同格の期待ダメージが揃う**（同格で物理×0.83／魔法×0.733）。
  上限を物理2.4・魔法2.7にしているのはこの比。あるけみすとも同じ構図だが、
  向こうのレンジ（魔法INT×2.6〜3.55／物理STR×2.2〜2.4）をそのまま使うと**魔法職だけ2割強くなる**
- **発動率は85%以上に置き、強さは倍率で調整する**。あるけみすとも75〜100%が大半で、
  60%以下はメテオストライク60%・フルハウス20%くらい（旅人＝初期職も95/85/80%）。
  発動率を50%台まで下げると初期職としては出ない技だらけになる。
  「威力が高い技を90%以上にしない」「軽い技は90%以上出る」はテストで固定している
- **多段スキルは `noCrit`（クリティカルしない）にする**。クリの固定加算はどの倍率にも同じだけ乗るので、
  多段ほど恩恵が大きくなり調整不能になる。クリを切ったぶん素の倍率を上げて釣り合わせる。
  「多段は必ず noCrit」「合計倍率が単発の主力を超えない」「職業ごとの主力の実質倍率が2割以上開かない」を
  テストで固定している
  （※2026-08-12に爆裂拳 0.7×4＝合計2.8 で格闘家が全職に76〜98%勝つ状態を作った。これらはその再発検出）

**実質倍率＝(倍率＋副参照)×多段数×発動率**。ただし物理と魔法は防御の効きが違うので直接は比べられない。
最終的な確認は同格の期待ダメージと勝率シミュレーションで行う。

- **回復はHP回復もMP回復もINTを参照する**（あるけみすと準拠。神聖なる手＝INT×1.5）。
  最大HP/MPの％では計算しない＝HPを積むほど回復量まで伸びる歪みを作らないため。
  **回復系の発動率は80%**（あるけみすとの回復も75〜80%が中心）
- 実装済みは**ノーブル＋初期職6の計7職・各5個**
- ⚠**プレイヤーのスキルには状態異常（`ail`）をまだ付けていない**。
  いまプレイヤー側が状態異常を撒く手段はエンチャントのルーンだけ（敵の技は2026-08-17に対応済み）
- 職業ごとのスキルの割り当ては旧版の実装（`Game.jsx` の `executeSkill`）から拾った。
  正はDBの `skills` テーブルなので、ズレがあれば直す

同格（戦闘力534どうし・HP534）に対する1ターンの期待ダメージ：

## サーバー権威

旧版はクライアントからステータスを書き換えられる穴を抱えたままなので、v2は最初から
**すべての更新をRPC経由**にする。

- `v2_profiles` にはSELECTポリシーしか無い＝クライアントから直接INSERT/UPDATEできない。
- `v2_apply_exp(uuid, int)` … EXP付与とLVアップ抽選の本体。SECURITY DEFINER。
  **PUBLIC/anon/authenticated からREVOKE済み**（＝直接呼べない）。EXP源となるRPCの中からだけ呼ぶ。
- `v2_create_character(text)` … キャラ作成。authenticated のみ。
- `v2_change_job(text)` … 転職。LV100の判定・転職条件（回数と証）・リセット・振り分け・スキル習得をすべてサーバーで行う。authenticated のみ。
- `v2_set_skills(jsonb)` … スキル編成の保存。使えるスキルか・枠数・想定利用MPが最大MPを超えないかをサーバーで検証する。authenticated のみ。
- `v2_set_favorites(jsonb)` … お気に入りの保存。実在するスキル名だけ受け付ける。authenticated のみ。
- `v2_debug_gain_exp(int)` … 成長確認用にEXPを自分へ入れる。**is_admin限定・開発用**。
  本番のEXP源（戦闘など）を作ったら、そちらから `v2_apply_exp` を呼び、このRPCは公開しない。

抽選ロジックはJS（表示・シミュレーション用）とSQL（正）の2箇所にある。
**片方だけ直すと表示と実値がズレる**ため、`STAT_KEYS` の並びと `unit`・定数は必ず同時に直すこと。
並び順は `src/v2/lib/stats.test.js` が固定している。

v2のSQLは `supabase_v2_core.sql` **1ファイルにまとめる**（分割しない）。全体が冪等なので、
仕様を足すたびに全文を流し直す運用にする。旧版で起きた「後から流したSQLが前の定義を巻き戻す」事故を避けるため。
